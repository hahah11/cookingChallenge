# CookingChallenge Frontend — Implementation Plan

**Status:** Approved 2026-08-06, not started. Implements Phase 7 of
[`openapi-first-api-plan.md`](openapi-first-api-plan.md) and everything that follows it.

## Context

`frontend/` is an untouched `ng new` scaffold (Angular 22, Vitest, Prettier — no routes, no HTTP, empty `styles.scss`). Everything else is ready: the backend implements **all 24 operationIds** in `openapi/cookingchallenge-api.yaml`, and the UI is fully specified by the Claude Design prototype (`CookingChallenge Frontend.dc.html`) plus [`frontend-prd.md`](docs/cookingChallenge/frontend-prd.md).

Phase 7 of [`openapi-first-api-plan.md`](docs/cookingChallenge/plans/openapi-first-api-plan.md) — "Frontend client codegen, deferred until the Angular project is scaffolded" — is what this plan unblocks, then carries through to the complete app.

The Modernist design system and the prototype were both read directly from Claude Design during planning, so exact token values, component classes, and UI copy are known and pinned below rather than approximated.

**Outcome:** a mobile-friendly Angular 22 app covering all 11 screens for organizer/admin, cook, guest, and public roles, with its HTTP client generated from the OpenAPI contract via `npm run generate:api`.

**`frontend/proxy.conf.json`:** `/api` → `http://localhost:8080`, `changeOrigin: true`. Wire `proxyConfig` into `angular.json`'s `serve` → `development` configuration as well, so `ng serve` works without the npm script.

**Verify the generated output** before building on it — these spec constructs are the ones that commonly generate awkwardly:

| Spec construct | Check |
|---|---|
| `ParticipantChallenge.mySubmission` (`nullable` + `allOf`) | May emit an inline `ParticipantChallengeMySubmission` model instead of reusing `MyScoreSubmission` |
| `ChallengeResult.categoryWinners` (`additionalProperties: Tsid`) | Should be `{ [key: string]: string }` |
| `RivalryDetail` (`allOf`) | Should flatten into one interface, not a nested composition |
| `GET /challenges/{id}/image` (`image/*`) | Should return `Blob` (`responseType: 'blob'`) |
| `PATCH /challenges/{id}/image` (multipart) | Should accept a `Blob`/`File` and build `FormData` |
| Enums (`Category`, `DishLabel`, `SystemRole`, `ChallengeStatus`) | Usable as `Category.GESCHMACK` under `isolatedModules` |

If any shape is wrong, **fix the spec and regenerate** — never patch the output.

## Phase 0b — Spec and backend amendments

Three display-name gaps block core screens. All are additive; no existing field changes meaning.

**1. Cook display names.** The History grid ("Marco & Lea"), the detail header, and the results table (cook first names above each tinted column) have no name source today.

- `CookAssignment` (organizer-facing): add required `name: string`.
- `ParticipantCookAssignment`: add nullable `name: string` — **null until REVEALED**, exactly like the existing `accountId`, so blind scoring stays blind.
- `ChallengeResult.cookAssignments[]` inherits `CookAssignment`, so it is covered by the first change.

Backend fills these through the existing `auth.AccountLookup` port — the same cross-module pattern `RivalriesListService` already uses to resolve `cookAName`/`cookBName`. No new port, no client-side join.

**2. Guest greeting.** `GuestHome` gains required `displayName: string` (first name) so `/home` can render "Hi, Felix". Guests get 403 on `/accounts`, so there is no alternative source.

**3. First/last name split.** `Account`, `CreateAccountRequest`, and `UpdateAccountRequest` move from a combined `name` to `firstName` + `lastName`, matching the already-split `PublicRegistrationRequest` and the domain's `Account.create(email, firstName, lastName, role)`.

- Keep a derived read-only `name` on `Account` for the Accounts table and open-challenge guest list, which the PRD specifies as full names.
- `GuestSubmissionStatus.name` stays as-is (display-only).

**Execution order:** edit `openapi/cookingchallenge-api.yaml` → `redocly lint` (expect the 2 known warnings: missing `info.license`, `/config` has no 4xx) → `./gradlew build` regenerates the server interfaces → update the affected mappers/services and their tests → then run `npm run generate:api`.

## Phase 1 — Design system (Modernist → SCSS)

Ported from the live `styles.css` in Claude Design project `8bb140f5-…`. Values below are exact — do not re-derive them.

```
src/styles/
  _tokens.scss        # :root custom properties (ported 1:1)
  _base.scss          # reset, body, headings, links, focus-visible, ::selection
  _buttons.scss       _forms.scss     _cards.scss     _tags.scss
  _nav.scss           _tables.scss    _dialog.scss    _utilities.scss
  _plate-color.scss   # project addition
  _overrides.scss     # project deltas
src/styles.scss       # @use the partials
```

**Tokens.** Surfaces `--color-bg #f3f2f2`, `--color-surface #eae9e9`, `--color-text #201e1d`; accents `--color-accent #ec3013`, `--color-accent-2 #e15b47`; `--color-divider: color-mix(in srgb, #201e1d 40%, transparent)`. Three 9-step OKLCH-derived ramps (`--color-neutral-100…900`, `--color-accent-100…900`, `--color-accent-2-100…900`). Spacing `4 / 8 / 12 / 16 / 24 / 32px` as `--space-1…8`. **All three radii are `0px`** — Modernist is a square-corner system; do not soften it. Shadows `--shadow-sm/md/lg` are ink-tinted `color-mix` on `#2d2b2b`.

**Typography.** Archivo 400/600/800, headings at weight 800, `line-height 1.12`, `letter-spacing -0.015em`. Body `15px / 1.55`. Scale: h1 42, h2 32, h3 25, h4 20, h5 16, h6 13 (h6 uppercase, `letter-spacing 0.08em`). Replace Modernist's `@import url(fonts.googleapis.com…)` with self-hosted `@fontsource/archivo` — the CDN import is render-blocking and leaks visitor IPs.

**Component classes to port:** `.btn` (+ `-primary/-secondary/-ghost/-icon/-block`), `.field`/`.input`/`.radio`/`.seg`, `.card` (+ `-kicker/-title/-body/-meta`), `.elev-sm/md/lg`, `.tag` (+ `-accent/-accent-2/-neutral/-outline`), `.nav`/`.nav-brand`, `.table`, `.dialog`/`-backdrop`/`-title`/`-body`/`-actions`, `.hr`, `.text-muted`.

**Project overrides (`_overrides.scss`):**

- **`.btn-primary` is black** — `#1a1a1a`, hover `#333`, active `#000` — not Modernist's red accent. This is a standing preference in PRD §8, and the prototype overrides it the same way.
- **One `.tag-success`** for the "Revealed" chip (`background #dbead9`, `color #2f6b34`). The prototype inlines this in three places while using `.tag-accent` for the same concept in three others — resolve to a single class.
- Focus-visible rings, hit targets ≥44px, and `@media (prefers-reduced-motion)` for the reveal animation.

**`_plate-color.scss` — plate colors are data, not constants.** `PlateColor.hexCode` comes from `GET /api/v1/config`; the prototype's hardcoded `RED #c0392b` / `YELLOW #e0b400` is a shortcut. Drive tinting from a CSS custom property set inline from the API value:

```scss
.plate-solid { background: var(--plate-color); color: #fff; }
.plate-tint  { background: color-mix(in srgb, var(--plate-color) 13%, transparent); }
.plate-swatch{ background: var(--plate-color); }
```

bound as `[style.--plate-color]="assignment.hexCode"`. Never conveys meaning by color alone — pair every tint with text or an icon (WCAG AA).

## Phase 2 — Core layer

```
src/app/core/
  api/generated/        # gitignored
  api/api-config.ts     # Configuration provider, basePath from environment
  auth/auth.ts          # @Service — token, claims, login, accessLinkLogin, logout
  auth/jwt-claims.ts     auth/auth-guard.ts     auth/organizer-guard.ts
  config/app-config.ts  # @Service — GET /config, cached, provideAppInitializer
  http/auth-interceptor.ts   http/error-interceptor.ts
  errors/api-error.ts   # typed ErrorBody + code union
  notifications/notification.ts
```

**`app.config.ts`** gains `provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]))`, `provideAppInitializer(() => inject(AppConfig).load())`, the generated `Configuration` provider, and `provideRouter(routes, withComponentInputBinding())`.

**Auth.** Both login paths return the same `{ accessToken, expiresAt }`. Store in `sessionStorage` behind a signal. There is **no `/me` endpoint**, so `sub` (accountId) and `roles` come from decoding the JWT payload client-side — decode only, never verify; the backend is the authority. `roles` drives which shell renders; **selectable roles still come from `GET /api/v1/config`**, never hardcoded, per `docs/frontend/01-architecture.md#app-configuration-and-permissions`.

**Error interceptor.** Maps the `{error:{code,message,details,requestId,timestamp}}` envelope to a typed `ApiError`. Codes the UI switches on: `VALIDATION_ERROR` (has `details[]` → bind to form fields), `INVALID_CREDENTIALS`, `INVALID_OR_EXPIRED_LINK`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_A_PARTICIPANT`, `NOT_FOUND`, `ACCOUNT_ALREADY_EXISTS`, `CHALLENGE_NOT_OPEN`, `INVALID_STATE`.

> **The backend generates a fresh RSA keypair on every restart** (`JwtConfig`), so every token dies with the server. A 401 must clear the session and route to `/login` (organizer) or an "your link expired, ask the host to resend" screen (participant) — not fail silently.

## Phase 4 — Routing and shells

```
''                          → role-aware redirect (organizer → /challenges, else /home)
'login'                     → OrganizerLogin                       [public]
'register'                  → PublicRegistration (?token=)         [public]
'home'                      → ParticipantHome (?token=)            [authenticated]
'challenges'                → ChallengeHistory                     [organizer]
'challenges/:id'            → ChallengeDetail                      [organizer]
'challenges/:id/score'      → BlindScoring                         [authenticated]
'challenges/:id/results'    → ChallengeResults                     [authenticated]
'accounts'                  → AccountsAdmin                        [admin]
'rivalries'                 → RivalryList                          [organizer]
'rivalries/:cookA/:cookB'   → RivalryDetail                        [organizer]
'**'                        → NotFound
```

**`/home` and `/register` are contractually fixed** — the backend hardcodes `{app.frontend.base-url}/home?token=` and `/register?token=` in `SendChallengeInvitationsService` and `CreateRegistrationInviteService`. Do not rename them.

`/home` reads `?token=`, POSTs it to `/auth/access-link-login`, stores the JWT, then strips the query param via `router.navigate([], {replaceUrl: true})`. The link token is **reusable until its own 30-day expiry** while the JWT caps at 1 day — so re-opening the emailed link is the intended refresh path (there is no refresh endpoint).

Every feature route is lazy (`loadComponent`/`loadChildren`), per AGENTS.md.

Two shells: `OrganizerShell` (the `.nav` bar — brand, History / Accounts / Rivalries with `aria-current`, organizer name, Log out) and a bare `ParticipantShell`. The prototype's floating `.proto-nav` dev switcher must not ship.

## Phase 5 — Organizer features

**Login** (`features/auth/`). Signal Form, email + password, copy: kicker "CookingChallenge", title "Organizer log in", note *"Cooks and guests don't log in here — they get a personalized link by email for each challenge."* The prototype's three "Preview a … link →" buttons are prototype navigation — drop them. Add a real error state for `INVALID_CREDENTIALS` (the prototype has none).

**History** (`features/challenges/`). `GET /api/v1/challenges` (paginated). Grid `repeat(auto-fill, minmax(260px, 1fr))`. Kicker "Cook-off history", h1 "Challenges", primary "New challenge". Card meta: status tag + `{submittedGuestCount}/{totalGuestCount} submitted`, or "Results ready" when revealed. When `overallWinnerAccountId` is set, that cook's name gets the winner chip. Needs an empty state and pagination — the prototype has neither.

*New challenge dialog:* photo drop (4:3), Title, Date, Dish name, Cook A/Cook B selects, guest checkbox list. Two calls sequenced as one dialog — `POST /challenges` then `PATCH /challenges/{id}/image` — because `CreateChallengeRequest` deliberately has no image field. Filter the cook already chosen for A out of B's options (the prototype allows picking the same person twice).

**Challenge detail.** Two primary calls by state: `GET /challenges/{id}/status` while OPEN (guest list + per-guest `submitted`), `GET /challenges/{id}/results` once REVEALED.

- *Open:* guest rows (full names per PRD §8) with `Submitted`/`Pending` tags; actions **Send links**, **Edit cooks & guests**, **Registration QR code**, **Reveal results**. "Links sent ✓" flashes for 3s after `POST /invitations`.
- *Revealed:* `results-table` + the unreveal footer, copy *"Made a mistake? You can reopen scoring and hide the results again."*
- Reveal plays the full-screen "REVEALED!" overlay (scrim fade + `revealPop` scale/rotate, 1100ms) — gated behind `prefers-reduced-motion`.
- **Copy fix:** the reveal confirmation says *"This can't be undone."* while an Unreveal button sits beside the results. Change to *"…and closes scoring. You can reopen it later if you need to."*

All four dialogs (Send links, Edit cooks & guests, QR, and the two confirms) **fetch fresh on open** — never reuse the parent page's state, per the standing data-loading rule.

**Accounts** (`features/accounts/`). `GET /accounts` → table Name / Email / Roles / (edit). Edit dialog re-fetches via `GET /accounts/{id}`. Role checkboxes are built from `config.availableRoles`; `USER` is checked and disabled. Needs empty state + pagination.

**Rivalries** (`features/rivalries/`). `GET /rivalries` cards; `GET /rivalries/{a}/{b}` detail. Render the server's `headline` verbatim — it is pre-rendered display text. Empty state: *"No revealed challenges yet — rivalries build up once results come in."*

## Phase 6 — Participant and public features

**Participant home** (`features/home/`). `GET /me/home` → `open` / `past`. One screen serves both guest and cook — branch on the per-challenge flags, never on role:

| Flag | UI |
|---|---|
| `canScore && !submitted` | "Score now" (`btn-primary`) |
| `canScore && submitted` | "Edit scores" (`btn-secondary`) + tag "Submitted — editable until reveal" |
| `canPickColor` | two plate-color swatch buttons (**with accessible names** — the prototype's are empty buttons) |
| cook, color already picked | swatch + *"You're plating **{colorName}** — noted for guests once scoring opens."* |
| `status === REVEALED` | "Revealed — view results" → `/challenges/{id}/results` |

Empty state: *"Nothing open right now — check back after the next cook-off."*

**Blind scoring.** `GET /challenges/{id}` → `ParticipantChallenge`; pre-fill from `mySubmission`. Grid `1fr 2fr 2fr`: column headers are solid plate-color bars driven by `participantCookAssignments[].colorId` → `config.plateColors`; **`accountId` is null until reveal** — that's the blindness, honour it. Three category rows labelled from `categories` (Mundgefühl / Tellersprache / Geschmack), 1–5 stars each. Submit disabled until all 6 values are set. `POST /scores` returns 201 first time, 200 on edit; 409 means someone revealed mid-edit → show that, don't retry.

**Results.** `GET /challenges/{id}/results`, same `results-table`, no unreveal control. The frontend sums `categoryTotals` for the Total row — deliberate per the spec (plain arithmetic, not business logic).

**Color pick.** `POST /challenges/{id}/color-pick` after a confirm dialog: *"This locks your plate color for this challenge and assigns the other cook the remaining color automatically. This can't be changed afterward."* 409 means the other cook picked first — refresh, don't error out.

**Public registration** (`features/register/`). `/register?token=` → form (First name / Last name / Email) → `POST /public/registrations`. Render the server's `message` verbatim for both outcomes (`joined` true/false). Handle 401 (`INVALID_OR_EXPIRED_LINK`) with a clear "this code has expired" state and 409 for a duplicate email — the prototype has neither.

## Phase 7 — Responsive, a11y, CI, docs

**Responsive.** The prototype has **zero media queries** and four layouts that break on a phone: the detail/results header (hard 50/50 text+photo `flex`, no wrap), rivalry and home cards (same split), the `1fr 2fr 2fr` scoring grid with five 28px stars per cell, and the 4-column Accounts table. Fix with `flex-wrap` + a `min-width` breakpoint at 640px, a card-list fallback for Accounts below 640px, and smaller stars with larger hit targets on touch.

**A11y.** AXE-clean and WCAG AA are non-negotiable per AGENTS.md. Specific carry-overs from the prototype to *not* copy: `<span>★</span>` with no role or tabindex, unlabelled color-choice buttons, dialogs missing `aria-labelledby`, no focus trap or Escape, winner conveyed by color alone. Add `vitest-axe` assertions to each screen's spec.

**CI** — new `frontend` job in `.github/workflows/tests.yml`: `actions/setup-node` (Node 26 to match `packageManager: npm@11.17.0`), `actions/setup-java` (the generator needs a JRE), `npm ci`, `npm run generate:api`, `npm run lint`, `npm test -- --run`, `npm run build`. Also fix the existing backend job: it runs bare `gradle`, not `./gradlew`.

**Docs to reconcile** (they currently contradict the code you'll be writing):

- `frontend/CLAUDE.md` step 2 says "Create model/interfaces matching backend DTOs" — contradicts OpenAPI-first codegen. Rewrite as "run `npm run generate:api`; never hand-write API models."
- `docs/frontend/05-performance-testing.md` teaches `jasmine.createSpyObj` throughout; the project runs Vitest. Port to `vi.fn()`.
- `docs/frontend/01-architecture.md` §File Naming Conventions specifies `*.component.ts`; the project uses v20+ suffix-less naming.
- `docs/frontend/02-components.md` / `04-routing-forms-http.md` use `@Input`/`@Output`, constructor injection, explicit `OnPush`; AGENTS.md mandates `input()`/`output()`/`inject()` and forbids explicit `OnPush`.

## Deliberate deviations from the prototype

The prototype is the design spec for structure, copy, and tokens — but it is a mockup, and these parts are shortcuts, not intent:

| Prototype | Real app |
|---|---|
| QR via `api.qrserver.com` encoding a raw `challengeId` | Local QR render of the opaque `registrationUrl` token. Encoding the raw id would let anyone self-register into any challenge |
| Fake login, hardcoded `GUEST_ID=6` / `COOK_ID=2` | Real JWT auth + access-link token exchange |
| Reveal fills results with `3 + random(2)` | Server-computed `categoryTotals` / `categoryWinners` |
| Hardcoded `RED #c0392b` / `YELLOW #e0b400` | `config.plateColors[].hexCode` |
| No loading, error, or most empty states | Added throughout (see Phase 3) |
| No media queries | Responsive down to 375px |
| Mouse-only stars, unlabelled buttons, no focus trap | Full keyboard + AXE-clean |
| Winner = most category wins (can contradict the Total row) | `overallWinnerAccountId` from the server |
| `.proto-nav` floating switcher | Removed |
| Dead bindings (`redDisabled`, `rivalryText`, `sendLinks()`, `photoSlotId`) | Not carried over |

## Verification

1. **Codegen standalone:** `cd frontend && npm run generate:api` → client appears under `src/app/core/api/generated/`, 7 API services + ~60 models, `npx tsc -p tsconfig.app.json --noEmit` clean.
2. **Codegen is automatic:** delete the generated folder, run `npm start` → the `prestart` hook regenerates it before the dev server boots. This is the acceptance criterion for "runnable through package.json".
3. **Spec drift:** change a description in the yaml, run `npm run generate:api:check` → non-zero exit.
4. **Backend up:** `cd backend && ./gradlew bootRun` (docker-compose starts Postgres automatically). Confirm `curl localhost:8080/api/v1/config` returns roles + plate colors.
5. **Organizer end-to-end:** log in → create a challenge with a photo → open detail → Send links → **read the access link from the backend console** (`LoggingNotificationAdapter` logs it; email is a stub) → Registration QR → Reveal (confirm the animation and the score table) → Unreveal.
6. **Guest end-to-end:** paste the logged link into the browser (`/home?token=…`) → verify the JWT exchange and that `?token=` is stripped → score 6 values → resubmit to confirm edit-until-reveal → view results after the organizer reveals.
7. **Cook end-to-end:** access link → pick a plate color → confirm the picker disappears for both cooks and the other color is auto-assigned.
8. **Public:** generate a QR, scan or open its `registrationUrl` → register → confirm the account joins the challenge, and that the same QR works for a second walk-in.
9. **Restart resilience:** restart the backend mid-session (this rotates the RSA keypair) → confirm the 401 path routes cleanly rather than hanging.
10. **Quality gates:** `npm test -- --run` (incl. `vitest-axe`), `npm run lint`, `npm run build` under the 500kB initial budget, and a manual pass at 375px width.
11. **Backend regression** after Phase 0b: `./gradlew build` green, all existing tests passing.

# CookingChallenge Frontend — Implementation Plan

**Status:** Approved 2026-08-06. Design system swapped from Modernist to Angular Material 3 on 2026-08-07 (see [`design-reference.md`](../design-reference.md)) — nothing had been built yet, so this is a pivot, not a rewrite. Implements Phase 7 of
[`openapi-first-api-plan.md`](openapi-first-api-plan.md) and everything that follows it.

**Phase 0, Phase 0b, Phase 1, Phase 2, Phase 3, Phase 4, and Phase 5 are done (2026-08-10)** — see their sections below for implementation notes and deviations. `frontend/` now has a working, verified OpenAPI client codegen pipeline, the spec/backend name gaps are closed, the Angular Material 3 design system is wired and building clean, the core layer (auth, config, HTTP interceptors, typed errors, notifications) is in place, the full shared component library (`src/app/shared/components/`) exists with unit tests, the full route table with both shells is wired end to end, and every organizer-facing screen (login, challenge history + creation, challenge detail with its full open/revealed lifecycle, accounts admin, rivalries) is implemented against the real API. **Phase 6 (participant and public features) is next, not started.**

## Context

`frontend/` is an untouched `ng new` scaffold (Angular 22, Vitest, Prettier — no routes, no HTTP, empty `styles.scss`). Everything else is ready: the backend implements **all 24 operationIds** in `openapi/cookingchallenge-api.yaml`, screen structure/copy/flows are fully specified by the Claude Design prototype (`CookingChallenge Frontend.dc.html`, project `6749cf81…`) plus [`frontend-prd.md`](docs/cookingChallenge/frontend-prd.md), and the visual system is fully specified by the companion Material 3 design system (`CookingChallenge.dc.html`, project `eddd583d…`, design system `cookoff-material-3-98ca423e-…`).

Phase 7 of [`openapi-first-api-plan.md`](docs/cookingChallenge/plans/openapi-first-api-plan.md) — "Frontend client codegen, deferred until the Angular project is scaffolded" — is what this plan unblocks, then carries through to the complete app.

Both Claude Design projects were read directly during planning, so exact token values, component inventory, and UI copy are known and pinned below rather than approximated.

**Outcome:** a mobile-friendly Angular 22 app covering all 11 screens for organizer/admin, cook, guest, and public roles, with its HTTP client generated from the OpenAPI contract via `npm run generate:api`.

## Phase 0b — Spec and backend amendments

**Done (2026-08-07).** All three gaps closed in the spec and backend; 268 backend tests pass, `./gradlew build` green.

Implementation notes/deviations:
- The assumed domain factory `Account.create(email, firstName, lastName, role)` **did not exist** — `Account` had a single `name` field and `Account.create(Email, String name, SystemRole...)`. Splitting to `firstName`/`lastName` was therefore a real domain change (new `renameFirst`/`renameLast` methods, derived `getName()`), not just a DTO/mapper edit as implied below.
- Because `Account` is persisted, this also needed a **Liquibase migration** (`008-account-name-split.yaml`, not scoped in this doc originally): add `first_name`/`last_name` columns, backfill by splitting the existing `name` value on the first space, `NOT NULL`, then drop `name`.
- `CookAssignment.name`/`ParticipantCookAssignment.name`/`GuestHome.displayName` resolution required threading `AccountLookup` as a new constructor parameter into `ChallengeModelMapper.cookAssignments(...)` and `.toParticipantChallenge(...)`, and injecting `AccountLookup` into `ListChallengesService`, `PickColorService`, `GetChallengeForParticipantService`, and `HomeService`, which didn't have it before — a wider blast radius than "amend the mappers."

Three display-name gaps block core screens. All are additive; no existing field changes meaning.

**1. Cook display names.** The History grid ("Marco & Lea"), the detail header, and the results table (cook first names above each tinted column) have no name source today.

- `CookAssignment` (organizer-facing): add required `name: string`.
- `ParticipantCookAssignment`: add nullable `name: string` — **null until REVEALED**, exactly like the existing `accountId`, so blind scoring stays blind.
- `ChallengeResult.cookAssignments[]` inherits `CookAssignment`, so it is covered by the first change.

Backend fills these through the existing `auth.AccountLookup` port — the same cross-module pattern `RivalriesListService` already uses to resolve `cookAName`/`cookBName`. No new port, no client-side join.

**2. Guest greeting.** `GuestHome` gains required `displayName: string` (first name) so `/home` can render "Hi, Felix". Guests get 403 on `/accounts`, so there is no alternative source.

**3. First/last name split.** `Account`, `CreateAccountRequest`, and `UpdateAccountRequest` move from a combined `name` to `firstName` + `lastName`, matching the already-split `PublicRegistrationRequest` and the domain's `Account.create(email, firstName, lastName, role)`.

- Keep a derived read-only `name` on `Account` for the Accounts table and open-challenge guest list, which the PRD specifies as full names.
- `GuestSubmissionStatus.name` stays as-is (display-only).

**Execution order:** edit `openapi/cookingchallenge-api.yaml` → `redocly lint` (expect the 2 known warnings: missing `info.license`, `/config` has no 4xx) → `./gradlew build` regenerates the server interfaces → update the affected mappers/services and their tests → then run `npm run generate:api`.

## Phase 1 — Design system (Angular Material 3)

**Done (2026-08-07).** `frontend/src/styles/` has `_theme.scss`, `_typography.scss`, `_icons.scss`, `_plate-color.scss`, `_overrides.scss`, assembled by `styles.scss` exactly as spec'd below. `npx ng build`, `npx tsc -p tsconfig.app.json --noEmit`, and `npm run lint` all pass clean.

Implementation notes/deviations:
- **Color integration uses `mat.theme-overrides()`, not a reconstructed Sass palette.** Angular Material's M3 color-role generator (`node_modules/@angular/material/core/tokens/m3/_md-sys-color.scss`) turned out to use the exact same role→tone mapping as the CookOff tokens (e.g. `on-primary-container` = primary tone 30 in both), and its typescale/shape/elevation/state generators already emit the exact same values as `tokens/typography.css` / `tokens/shape.css` / `tokens/elevation.css` (verified by reading the generator source, not assumed) — standard, unmodified M3. So instead of converting every OKLCH tone to hex and rebuilding a Sass palette map (error-prone, and against "explicit palette values, not a re-derived seed"), `_theme.scss` calls `mat.theme()` once with a structural placeholder palette (only to emit the typography/shape/elevation/state tokens, which need no further changes), then `mat.theme-overrides()` maps every `--mat-sys-<role>` straight onto the matching `--md-sys-color-<role>` custom property. Because those already switch under `[data-theme="dark"]`, this one mapping keeps light and dark pixel-for-pixel with no second `theme()` call.
- **Raw `--md-sys-shape-corner-*`, `--md-sys-elevation-level-*`, `--md-sys-motion-*`, and `--md-sys-spacing-*` tokens live in `_theme.scss`'s `:root` block**, copied verbatim from the design project (not spec'd as a separate file in the plan, but needed since `_plate-color.scss` and future hand-built components — nav-bar, star-rating — consume them directly; Material's own components compute shape/elevation from `mat.theme()` internally and don't read these).
- **Success color triad values are a project invention**, not sourced from the design project (its `tokens/colors.css` has no success role, confirmed by reading the file). Generated at OKLCH hue 145° using the same per-tone chroma curve as the error role, at the same four tones every other M3 pair uses (40/100/90/10 light, 80/20/30/90 dark) — see `_overrides.scss` for the values and reasoning inline. Revisit if a real brand green exists.
- **`MatIconRegistry.setDefaultFontSetClass('material-symbols-outlined')` was wired into `app.config.ts`** (via `provideAppInitializer`) even though icon registration wasn't explicitly scoped to Phase 1 vs. Phase 2's core layer — icons are inert without it, so it shipped now rather than leaving a half-finished Phase 1.
- **Two build fixes needed**: `provideAppInitializer`'s callback must return `void`/`Observable`/`Promise` — `MatIconRegistry.setDefaultFontSetClass()` returns `this` for chaining, so the callback needed an explicit block body. `@fontsource/roboto/400.css` (etc.) needed an explicit `@use '...' as roboto-400` — Sass rejects `400` as a default namespace since it isn't a valid identifier.
- **Material Symbols self-hosting ships the npm package's default full variable font** (`material-symbols-outlined.woff2`, ~3.9MB, no unicode-range subsetting) — it's a lazily-fetched font asset, not part of the JS initial bundle (which built to 73.68 kB estimated transfer, well under the 500kB budget), but flagging it as a possible follow-up if icon-load latency matters later.

Ported from the live tokens in Claude Design project `eddd583d-…`, design system `cookoff-material-3-98ca423e-…`. Values below are exact — do not re-derive them.

```
src/styles/
  _theme.scss          # mat.theme() with the CookOff M3 palettes (below)
  _typography.scss      # @font-face for self-hosted Roboto / Roboto Mono
  _icons.scss           # @font-face for self-hosted Material Symbols Outlined
  _plate-color.scss     # project addition, unchanged in spirit from before
  _overrides.scss       # project deltas, see below
src/styles.scss         # @use the partials, then Angular Material's core + theme
```

**Color.** M3 tonal palettes generated in OKLCH from the brand seed `#ec3013` (primary, hue 29°). Secondary is the same hue at low chroma; tertiary is an added herb-green (hue 100) — both are the design project's own inference, not sourced from the old Modernist system, so revisit them if a real secondary/tertiary brand color exists. Error uses hue 10. Full reference palettes (0–100, 25 stops each) live in `tokens/colors.css` in the design project; map system roles (`--md-sys-color-primary`, `-on-primary`, `-primary-container`, `-surface-container-*`, etc.) onto Angular Material's `mat.theme()` using explicit palette values, not a re-derived seed, so light **and** the existing `[data-theme="dark"]` scheme both match pixel-for-pixel. Since `--md-sys-color-primary` in the light scheme resolves to the brand red-orange itself, **the old Modernist project override forcing `.btn-primary` to black is gone** — Material's filled/primary button is already on-brand.

**Typography.** Roboto (400/500/700) + Roboto Mono (400/500), M3's reference typeface — not Archivo, which has no M3 counterpart (flagged as a substitution in the design project's readme, open to revisiting). Full 15-step M3 type scale (display/headline/title/body/label × large/medium/small) — sizes/line-heights/tracking are pinned in `tokens/typography.css`, feed them into Angular Material's `mat.typography-config()`. Self-host both via `@fontsource/roboto` + `@fontsource/roboto-mono` instead of the design's Google Fonts `@import` — same reasoning as the prior Archivo decision: the CDN import is render-blocking and leaks visitor IPs.

**Shape.** M3's 7-step corner scale: `none 0 / extra-small 4 / small 8 / medium 12 / large 16 / extra-large 28 / full 999px`. This **replaces** Modernist's all-zero-radius rule — buttons/chips are fully rounded (pill), cards use `medium` (12dp), dialogs use `extra-large`. Angular Material components apply this by default once themed; only the plate-color chips and any hand-built component need explicit `--md-sys-shape-corner-*` usage.

**Elevation.** 5 M3 levels, each a two-layer ink shadow (key + ambient) plus a surface-tint-opacity scale for tinted surfaces — no blur/glassmorphism. Comes for free from themed Material components (`mat-card`, `mat-menu`, `mat-dialog-container`, …); only hand-built surfaces need the raw `--md-sys-elevation-level-*` tokens.

**Interaction states.** M3 state layers — flat `currentColor` wash at 8% (hover) / 10% (focus, pressed) / 16% (dragged) opacity, not a color swap. Disabled controls drop to 38% content / 12% container opacity. Focus rings are a 2px primary-color outline, offset 2px. Angular Material implements this natively; don't override it per component.

**Iconography.** Material Symbols Outlined (Google's variable icon font), 24px default, `FILL 0` with a `.filled` modifier for toggled/selected states (e.g. a filled heart). Self-host via the `material-symbols` npm package rather than the design's Google Fonts CDN import, for the same privacy/perf reason as the type decision. Register with `MatIconRegistry.setDefaultFontSetClass('material-symbols-outlined')` so `<mat-icon>weekend</mat-icon>` resolves correctly. This replaces the earlier plan's assumption of inline Lucide SVGs — there were none actually in use yet, so no migration needed.

**Component inventory** (Angular Material module → design system component): `MatButtonModule` (filled/tonal/elevated/outlined/text), `MatIconButton`/`MatFabButton` (Icon Button, Fab), `MatCardModule` (elevated/filled/outlined), `MatChipsModule` (assist/filter/input/suggestion), `MatBadgeModule`, `MatDividerModule`, `MatFormFieldModule` + `MatInputModule` (TextField, outlined + filled, error state), `MatCheckboxModule`, `MatRadioModule`, `MatSlideToggleModule` (Switch), `MatToolbarModule` (TopAppBar — closest native equivalent, small + center-aligned via CSS), `MatTabsModule`, `MatDialogModule`, `MatSnackBarModule`, `MatProgressBarModule` + `MatProgressSpinnerModule`.

**Gap: NavigationBar (bottom nav).** Angular Material has no stock bottom-navigation-bar component — the design system's `NavigationBar` is a Material-*styled* pattern, not a real module. Build it from `MatTabsModule`'s low-level primitives or plain `<nav>` + `mat-icon` + `mat-ripple`, styled to the M3 nav-bar spec (indicator pill, 3–5 destinations, active-state color). Flag this in Phase 3 as a hand-built component, same treatment as `star-rating` below.

**Project overrides (`_overrides.scss`):**

- **One success color role** for the "Revealed" chip/tag. M3 has no built-in success role (only primary/secondary/tertiary/error) — the old Modernist plan resolved a similar inconsistency (three places used a bespoke `.tag-success`, three used `.tag-accent`) into one class; do the same here with a small custom `--cc-color-success`/`-on-success`/`-success-container` triad (not part of M3, a project addition) rather than repurposing tertiary, so "success" and "herb-green tertiary accent" stay visually distinct.
- Focus-visible rings, hit targets ≥44px (M3 spec already targets this on interactive components, verify on custom ones), and `@media (prefers-reduced-motion)` for the reveal animation — M3 motion tokens (`tokens/elevation.css`) define standard/emphasized easing and short/medium/long durations to animate with, but ship no signature bounce of their own; the reveal's `revealScrim`/`revealPop` keyframes are still a project addition on top.

**`_plate-color.scss` — plate colors are data, not constants, unchanged from the prior plan.** `PlateColor.hexCode` comes from `GET /api/v1/config`; the prototype's hardcoded `RED #c0392b` / `YELLOW #e0b400` is a shortcut. Drive tinting from a CSS custom property set inline from the API value:

```scss
.plate-solid { background: var(--plate-color); color: #fff; }
.plate-tint  { background: color-mix(in srgb, var(--plate-color) 13%, transparent); }
.plate-swatch{ background: var(--plate-color); }
```

bound as `[style.--plate-color]="assignment.hexCode"`, styled with M3 shape (rounded, not square) and elevation for consistency with the rest of the kit. Never conveys meaning by color alone — pair every tint with text or an icon (WCAG AA).

**Verify against `ui_kits/cookoff/`** in the design project before treating any component mapping above as final — it's a click-through recreation of the actual product screens and is the tie-breaker for anything ambiguous in the token/component-inventory lists.

## Phase 2 — Core layer

**Done (2026-08-07).** All files below exist as spec'd. `npx tsc -p tsconfig.app.json --noEmit`, `npx ng build` (77.64 kB estimated transfer, well under budget), `npm run lint`, and `npx ng test` all pass clean.

Implementation notes/deviations:
- **No `@Service` decorator.** AGENTS.md calls it out as available in Angular v22+, but it doesn't exist in the installed `@angular/core@22.1.0`'s public API (confirmed by grepping the package's `.d.ts` files) — used `@Injectable({ providedIn: 'root' })` throughout instead, matching `docs/frontend/03-services-state.md` and Phase 1's own `app.config.ts`.
- **`basePath` is a hardcoded empty string** (`provideApi('')` in `api-config.ts`), not read from an Angular `environment.ts` — there's no `environments/` folder or `fileReplacements` config in `angular.json`, and the app only ever talks same-origin (`proxy.conf.json` forwards `/api` in dev; the spec's `servers: [{ url: / }]` implies same-origin in prod too). Revisit if a real multi-environment `basePath` need ever shows up.
- **JWT claim shape confirmed against `JwtIssuer.java`**: only `iss`, `iat`, `exp`, `sub` (account id), and `roles` (always an array, even for one role) — no `role` singular, no challenge/cook/guest-scoping claims. `jwt-claims.ts` decodes exactly this shape.
- **`errorInterceptor` branches only on `apiError.code === 'UNAUTHENTICATED'`**, not on raw HTTP 401 status, so a 401 from a failed login (`INVALID_CREDENTIALS`) doesn't trigger a global logout+redirect — only a dead/expired session on an already-authenticated request does. Redirects to `/login` or `/home` based on the role captured *before* `auth.logout()` clears the claims signal; both routes are pinned by Phase 4 already, so referencing them now is safe even though the routes themselves don't exist until Phase 4.
- **`Notification`'s `success`/`info`/`error` are currently identical** (all a plain `MatSnackBar.open(...)`, 4s duration) — kept as three named methods rather than one, since call-site intent (`notification.error(...)`) matters even before per-severity styling (panel classes, colors) is added in a later phase.
- **`ApiError` extends the generated `ErrorBody`** (overriding `code` to a narrower union) rather than a hand-duplicated interface, plus an added `status: number` not in the wire envelope, for interceptor logic (e.g. distinguishing network failures, `status: 0`, from server-returned errors). Falls back to a synthetic `UNKNOWN_ERROR` when `httpError.error` isn't the expected `{error: ErrorBody}` shape (network/CORS failures never reach the backend).
- **`auth-guard.ts`/`organizer-guard.ts` redirect to `/` / `/home` / `/login`** even though none of these routes exist until Phase 4 — `Router.createUrlTree` doesn't validate the route exists at guard-definition time, and the target paths are already contractually pinned by Phase 4's route table.
- No `admin`-only guard yet — Phase 2's file list only specifies `auth-guard.ts` and `organizer-guard.ts`; the `/accounts` route's admin-only gating (route table marks it `[admin]`, stricter than `[organizer]`) is deferred to Phase 4, reusing `Auth.hasAnyRole(SystemRole.ADMIN)`.

```
src/app/core/
  api/generated/        # gitignored
  api/api-config.ts     # Configuration provider, basePath from environment
  auth/auth.ts          # @Service — token, claims, login, accessLinkLogin, logout
  auth/jwt-claims.ts     auth/auth-guard.ts     auth/organizer-guard.ts
  config/app-config.ts  # @Service — GET /config, cached, provideAppInitializer
  http/auth-interceptor.ts   http/error-interceptor.ts
  errors/api-error.ts   # typed ErrorBody + code union
  notifications/notification.ts
```

**`app.config.ts`** gains `provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]))`, `provideAppInitializer(() => inject(AppConfig).load())`, the generated `Configuration` provider, and `provideRouter(routes, withComponentInputBinding())`.

**Auth.** Both login paths return the same `{ accessToken, expiresAt }`. Store in `sessionStorage` behind a signal. There is **no `/me` endpoint**, so `sub` (accountId) and `roles` come from decoding the JWT payload client-side — decode only, never verify; the backend is the authority. `roles` drives which shell renders; **selectable roles still come from `GET /api/v1/config`**, never hardcoded, per `docs/frontend/01-architecture.md#app-configuration-and-permissions`.

**Error interceptor.** Maps the `{error:{code,message,details,requestId,timestamp}}` envelope to a typed `ApiError`. Codes the UI switches on: `VALIDATION_ERROR` (has `details[]` → bind to form fields), `INVALID_CREDENTIALS`, `INVALID_OR_EXPIRED_LINK`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_A_PARTICIPANT`, `NOT_FOUND`, `ACCOUNT_ALREADY_EXISTS`, `CHALLENGE_NOT_OPEN`, `INVALID_STATE`.

> **The backend generates a fresh RSA keypair on every restart** (`JwtConfig`), so every token dies with the server. A 401 must clear the session and route to `/login` (organizer) or an "your link expired, ask the host to resend" screen (participant) — not fail silently.
